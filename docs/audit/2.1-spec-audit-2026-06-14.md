## 🔴 致命（2 项）

### S01：MS-2.1-1 验证命令完全错误

**现状：** `grep -c '=> TokenKind::' crates/trust_parser/src/lexer.rs` 实测返回 **23**（标点 token 的 match 分支），而非 43。`static KEYWORDS` 使用 `(k, v)` 元组格式，不含 `=>`。

**修正：**
```bash
# 正确命令——统计 static KEYWORDS 映射条目
grep -cE '^\s*\("[a-zA-Z_]+"\s*,\s*TokenKind::' crates/trust_parser/src/lexer.rs
# 预期: 43
```

### S02：Step 1 自相矛盾——"cargo build 通过"不可行

**现状：** Step 1 删除 lexer 中 16 个 `TokenKind` 变体后，`parser.rs` 大量引用 `TokenKind::Loop`/`Select`/`Interface`/`Impl`/`BigIntLiteral`/`None_` 等，必然编译失败。Step 1 末尾写"可能有编译错误——记录并进入 Step 2"后又写"cargo build 通过"——两句矛盾。

**修正：** Step 1 验收条件改为：
> `cargo build -p trust_parser` 预期编译失败——记录错误清单到 `docs/phases/2/2.1/build-errors-step1.txt`；进入 Step 2 后随 parser 同步修复。

## 🟠 不一致（4 项）

### S03：Bang 被错误当作废弃 token

**现状：** Step 1/5 和 MS-2.1-3 要求从 `can_end_stmt`/`can_expr_start` 移除 `Bang`。但 `Bang`（`!`）是活跃运算符——前缀 `!x`（逻辑非）+ 后缀 `expr!`（断言解包）。**Bang 不在 16 个废弃关键字之列。**

**修正：**
- Step 1/5：移除 `None_`/`BigIntLiteral`，**保留 `Bang`**
- MS-2.1-3 验证命令：正则中剔除 `Bang`：
  ```bash
  grep -A 20 'fn can_end_stmt' crates/trust_parser/src/lexer.rs | grep -E 'None_|BigIntLiteral'
  grep -A 20 'fn can_expr_start' crates/trust_parser/src/parser.rs | grep -E 'None_|BigIntLiteral|Loop'
  ```

### S04：MS-2.1-1 "TokenKind 枚举 43 个变体"表述不精确

**现状：** 当前 `TokenKind` 枚举共 97 个变体（含字面量、标点、`Ident`、`Comment`、`Eof` 等）。删除 16+新增 5 后为 86 个变体。**43 是关键字/内置类型变体数量，非全部。**

**修正：** 改为"`TokenKind` 枚举中**关键字/内置类型相关的变体**恰好 43 个"。

### S05：Step 6 遗漏"同步本 Phase 修正特性"的新增规范

**现状：** TODO 2.1.7 明确要求同步 `number`=f64 类型规则、整数语义、位运算约束、块体函数强制返回标注、表达式体函数。Step 6 只写了"删除已废弃条目"，未覆盖新增规范同步。

**修正：** Step 6 增加子步骤：
> 4. 同步本 Phase 2 新增/修正的规范条目：`number`=f64 类型规则（2.2）、整数语义（2.2）、位运算约束（2.2）、块体函数强制返回标注（2.3）、表达式体函数语法（2.3）

### S07：测试编译失败处理机制缺失

**现状：** Step 7 的"失败清单"只适合运行时失败。`snap_loop`、`e2e_bigint`、`e2e_loop_break`、`e2e_break_value` 等引用即将删除的 AST 节点——**编译必然失败**，`cargo test` 根本跑不到收集清单阶段。

**修正：** Step 7 增加子步骤：
> 1a. 禁用/移除因 AST 删除而**无法编译**的测试（`snap_loop`、`e2e_bigint`、`e2e_loop_break`、`e2e_break_value`），记录到 `known-failures.md` 标记为"待 2.5 恢复/改写"
> 1b. `cargo build --workspace` 必须通过
> 2. `cargo test --workspace` 运行——此时仅有运行时失败可被收集；编译失败已在 1a 处理
