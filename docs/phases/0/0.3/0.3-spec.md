## 0. 文件说明

本规格书定义 **Phase 0.3**（三份文档交叉一致性审计）的工程范围、成功标准、审计流程和验收条件。

**背景：** Trust 当前有三份核心文档：
- `docs/Trust-设计文档.md`（A） — 语言设计（"为什么"）
- `spec/trust-spec.md`（B） — 语言规范（"是什么"）
- `docs/design-constraints.md`（C） — 编译器实现约束（"怎么实现"）

三份文档由不同阶段、多轮辩论迭代而成，必须通过系统化交叉审计确保它们之间没有矛盾、遗漏或过时的引用。

**一句话成功：** 三份文档之间的每一个交叉引用都可解析、每一处语义描述都一致、所有已知差异都已记录并分类（可接受 vs 待修正）。

## 1. 成功标准

**MS-0.3-1（交叉引用完备）：** 三份文档中所有 "详见 §X.Y" 跨文档引用均可解析到目标章节。死引用数量 = 0。

**MS-0.3-2（语义一致性）：** A↔B 之间无冲突——设计文档中描述的所有语言特性在规范中有对应的 REQ-ID，且规范中的 REQ-ID 覆盖了设计文档的全部语法特性。

**MS-0.3-3（差异分类）：** 所有审计中发现的不一致已记录于审计报告，并分为四类：
- **P0（阻塞）**：语义冲突，必须在 Phase 0 冻结前修正
- **P1（重要）**：定义缺失或措辞不精确，建议修正
- **P2（已知限制）**：已记录为设计取舍，不阻塞交付
- **P3（注释/示例）**：示例代码与规范不一致但不影响语义

## 3. 审计流程

### 3.1 审计 A↔B — 设计文档 × 语言规范

**步骤：**

1. **语法特性覆盖率检查：**
   - 逐项扫描设计文档 §2.1（保留特性列表）和 §11（语法参考与范例）中的所有语法特性
   - 对每个特性，在 `trust-spec.md` 中定位对应的 REQ-ID
   - 设计文档 §2.2（牺牲特性列表）中的每一项，验证在 trust-spec EBNF 中**不存在**
   - 产出：覆盖率矩阵（特性 → REQ-ID → 状态）

2. **所有权/并发语义一致性：**
   - 设计文档 §4.1–§4.5（所有权规则） → trust-spec OWN-REQ-001~008
   - 设计文档 §5.1–§5.5（并发模型） → trust-spec CON-REQ-001~005
   - 交叉验证每一条规则的文本描述是否与规范的 REQ 语义一致
   - 重点关注：三模式参数表、Channel 分离、select 语义、惰性 Future

3. **代码示例语法正确性：**
   - 抽样设计文档 §11 的代码示例（每子节至少 1 个），用 trust-spec 的 EBNF 验证语法合法性
   - 已记录的"❌ 编译错误"示例：验证该示例按照 trust-spec 的规则确实应该产生错误

### 3.2 审计 B↔C — 语言规范 × 实现约束

**步骤：**

1. **TIR 节点对应检查：**
   - `trust-spec.md` SEM-REQ-001（AST 节点定义）→ `design-constraints.md` §6.1（TIR 节点实现示例）
   - 验证：规范中定义的每个 AST 节点在 constraints 中有对应的 TIR 结构体
   - 验证：constraints §6.2 的借用检查器实现覆盖了 trust-spec OWN-REQ-001~008 的全部规则

2. **API 映射表一致性：**
   - `trust-spec.md` CON-REQ-004（Channel 分离）、OWN-REQ-002（三模式参数表） → `design-constraints.md` §9.2（ferro_rt API 映射表）
   - 验证：规范中的 Trust API 签名与 constraints 中的 Rust 映射一一对应

3. **错误格式对齐：**
   - `trust-spec.md` §9.1.1（JSON 错误格式） → `design-constraints.md` §8.2（JSON 格式示例）
   - 验证：JSON schema 中字段名、结构一致

### 3.3 审计 A↔C — 设计文档 × 实现约束

**步骤：**

1. 扫描设计文档中出现 "编译器应/需/会……" 的描述（如 §9.1 "编译器将 AST 翻译为 Rust 源码"、§4.1 "编译器会在后续使用 a 时给出建议"）
2. 在 constraints 中定位对应的实现规范条目
3. 记录无对应条目的描述，判定是否需要补充到 constraints

### 3.4 三方交叉引用审计

**步骤：**

1. 从三份文档中提取所有 `详见 §X.Y` / `见 §X.Y` / `对应 §X.Y` 的引用
2. 逐一验证目标章节真实存在
3. 验证引用的语义正确性（例如 "见 §5.2" 在上下文中确实指向正确的章节）

### 3.5 拒绝特性 EBNF 验证

**步骤：**

1. 列出设计文档 §15 的 8 个被拒绝特性
2. 逐一验证这些特性的语法在 trust-spec EBNF 中**确实不存在**
3. 验证这些特性在 design-constraints 中没有实现规范条目
4. 如果发现存在（如 `try/catch` 的 EBNF 遗迹），标记为 P0 并从 EBNF 中删除
