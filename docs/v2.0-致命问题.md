# Trust v2.0 设计文档 — 9项致命问题（阻塞设计验收）

> 来源：2026-06-14 第三轮辩论（debate-kimi R1），Kimi 对抗分析发现 45 条，Gate 裁决确认 9 项 🔴 致命  
> 审查对象：`docs/Trust-设计文档.md` (v2.0, ~1000行)

---

## K1 — §2.3 透明别名 vs §4.2 Receiver：类型身份矛盾

**问题：** `type Point = { x, y }` 声明为透明别名（不引入类型身份），但 `function Point.distance()` 把方法绑定到**名字**。匿名字面量 `{ x: 3, y: 4 }` 调用 `.distance()` 时，运行时如何知道它"属于"Point？

**引用：** §2.3 "不引入新的类型身份" vs §4.2 "方法绑定到名字 Point，同形状类型共享方法"

**影响：** 纯结构类型下，方法分派需要类型身份（Rust trait impl），透明别名不具备身份。这是文档在类型系统与方法系统之间的核心矛盾。

## K2 — §5.1 结构形状 Catch vs §5.1.1 枚举构造器 Codegen：互斥模型

**问题：** §5.1 说 `catch` "按结构形状匹配（不是按类型名）"，§5.1.1 生成的 Rust 代码却用 `ReadFileError::NotFound` 变体——这是按**名义构造器**匹配。两段对"错误如何被识别"给出互斥答案。

**引用：** §5.1 "结构形状匹配" vs §5.1.1 `Err(e @ ReadFileError::NotFound { .. })`

**影响：** 编译器无法同时实现两个模型。如果选结构形状，两个都含 `message: string` 的错误无法区分；如果选枚举构造器，则与拒绝 ADT 的设计冲突。

## K3 — §5.1 `throw` "必须是 Error" vs 示例直接 Throw 字面量：自相矛盾

**问题：** §5.1 说"`throw` 的参数必须是 `Error` 类型"，随后示例 `throw { message: "...", code: 404 }` 直接 throw 对象字面量，不调用 `Error()`。文档未定义 `Error` 是内置类型还是仅形状要求。

**引用：** §5.1 "throw 的参数必须是 Error 类型" vs `throw { message: "not found", code: 404 }`

**影响：** 若 `Error` 是具体类型，示例非法；若仅需形状要求，则"必须是 Error 类型"具有误导性。编译器无法在两种语义间做出一致实现。

---

## K4 — §10 `extern "rust"` FFI：所有权与错误传播完全未定义

**问题：** §10 仅给示例 `fn sqlx_query<T>(query: string, ...args): T` 并说"正确性是开发者责任"。0 行说明参数是 `&T` 还是 `T`、返回值谁拥有/如何 drop、泛型 T 如何映射 Rust trait、varargs 如何展开。

**引用：** §10 "声明不经过 Trust 所有权检查"

**影响：** 任何非 Copy 类型的 FFI 调用都无从实现。"开发者责任"不是规格——开发者不知道规则是什么。

---

## K5 — §5.1.1 穷举推断算法缺关键定义

**问题：** 固定点迭代算法缺泛型函数 E 参数化规则、高阶函数/闭包调用的 E 确定、32 层超限后的回退策略。

**引用：** §5.1.1 "编译器中收集 throw 形状...合并为当前函数的错误枚举...最大迭代深度 32，超限报错要求显式标注"

**影响：** "显式标注"的语法未定义——用户如何标注？用 `throws` 关键字？标注在函数签名什么位置？在泛型函数上怎么写？缺这些，编译器无法实现穷举检查。

## K6 — §2.6 Value 枚举 6 变体无法做形状校验

**问题：** §2.6 称 `unknown` 内部是 `Value` 枚举（null/bool/number/string/数组/对象），但"对象"变体是通用的——不知道字段名或类型。`case { name: string }` 与 `case { age: number }` 运行期无法区分。

**引用：** §2.6 "unknown 内部是一个可检视的动态载荷（编译器生成的封闭 Value 枚举）"

**影响：** 要支持形状校验，Value 必须携带类型描述符（字段名+类型信息），本质退化回动态类型检查。与"无虚表、无动态分发"承诺在性能/实现上无本质差异。

---

## K7 — §3.7 递归类型自动 Box 与结构等价冲突

**问题：** `type Node = { next: Node | null }` 自动 Box 后字段 Rust 类型是 `Box<Option<Node>>`，但匿名字面量 `{ next: null }` 是 `Option<Node>`。2^53 同形状但在 Rust 侧类型不同——结构等价被破坏。

**引用：** §3.7 "递归类型自动 Box"

**影响：** compiler 需要决定 Box 插入的策略（何时触发、插入位置、Box 后是否仍视为同形状），否则生成的 Rust 代码编译失败。

---

## K8 — §4.2 Go Receiver + 结构类型 → Rust Codegen 无对应机制

**问题：** Rust 方法分派依赖具体类型 + trait impl。结构类型下"同形状共享方法"需要为每个结构形状生成 trait，并为所有同形状类型实现。Rust orphan rule 限制跨 crate 实现。项目声称"编译到 Rust"但未提供可落地的映射方案。

**引用：** §4.2 "同形状类型共享方法" + §4.2 "导入路径决定使用哪个"

**影响：** 这是文档最根本的可实现性威胁——如果方法分派无法映射到 Rust，整个 Trust→Rust 编译器无法工作。

---

## K9 — §3.6 `shared` Number 原子优化与 `withLock` 语义冲突

**问题：** `number` 是 Copy 类型，`withLock(c => { c += 1 })` 中 `c` 是**副本**，修改 `c` 不影响原 `counter`。若说编译器特殊处理 Copy 类型的 withLock 参数为引用，文档未说明。

**引用：** §3.6 "对于 number 等支持原子操作的类型，编译器优化为原子指令" + 示例 `counter.withLock(c => { c += 1 })`

**影响：** 最核心的并发原语示例在 Copy 语义下是死代码——即使编译通过，运行时 counter 永远为 0。"原子优化"和闭包按值捕获不可调和。
